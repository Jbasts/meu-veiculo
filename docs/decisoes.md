# Decisões do projeto

Uma linha por decisão técnica relevante. Quando uma decisão mudar, não apague a antiga: acrescente a nova e diga qual substitui.

| Data | Decisão | Motivo | Alternativas consideradas |
|---|---|---|---|
| 29/09/2026 | Desenvolver com o Claude Code a partir deste kit | Ele cria, executa e corrige o projeto no próprio Windows da Paula, com PostgreSQL real | — |
| 29/09/2026 | Plataforma: aplicação web responsiva instalável (PWA) | Um só código para o computador (apresentação do TCC) e o celular; não exige loja, conta paga nem Mac; atualização imediata ao atualizar o servidor; a câmera funciona pelo campo de foto mesmo sem HTTPS. Offline não será prometido: as operações de dados exigem conexão | App multiplataforma com React Native + Expo (exige conta Apple ou Mac para instalar no iPhone, publicação e build próprios, mais ferramentas para aprender); app nativo |
| 29/09/2026 | Stack: React + TypeScript (Vite) no frontend, FastAPI (Python) no backend, PostgreSQL no banco | Preferência declarada pela Paula e adequada à PWA. TypeScript aponta, antes da execução, erros de tipo em campos de dinheiro, datas e respostas da API | JavaScript puro (menos verificação); outros frameworks de backend |
| 29/09/2026 | Aparelho de teste: Android, principalmente com o navegador Chrome | Celular que a Paula vai usar. Os testes de instalação da PWA, câmera e upload de fotos serão orientados para Android + Chrome. iPhone/Safari e HEIC vindo do iPhone ficam como compatibilidade documentada, não validada no aparelho | iPhone/Safari |
| 29/09/2026 | "Tipos de veículo" do pedido correspondem ao `tipo_combustivel` do veículo (flex, gasolina, etanol, diesel, gnv, hibrido, eletrico); não será criada coluna de tipo (carro, moto…) | O SQL não tem coluna de tipo de veículo; os valores `hibrido` e `eletrico` são os que exigem regras próprias (combustível não aplicável, GNV em m³). A compatibilidade de cada opção será documentada na etapa 7 | Criar coluna `tipo_veiculo` (carro, moto…) |
| 29/09/2026 | Arredondamento de dinheiro: meio para cima (`ROUND_HALF_UP`) para centavos, com `Decimal` no backend | É o arredondamento usual em valores monetários e o que o PDF usa (38,5 L × R$ 4,29 = 165,165 → R$ 165,17). O padrão do `Decimal` do Python (meio para o par) daria R$ 165,16; um teste vai garantir R$ 165,17. O `round()` do PostgreSQL para `numeric` já arredonda meio para cima | Meio para o par (arredondamento bancário) |
| 29/09/2026 | O botão "+" da tela "Usuários e veículos" cria a conta de outra pessoa sem senha: o sistema envia um link temporário de uso único para ela definir a própria senha | Nenhuma senha fixa é definida nem vista pelo administrador; reaproveita o mecanismo seguro da recuperação de senha. A conta criada começa com perfil `padrao` | Admin definir uma senha inicial; remover o botão |
| 29/09/2026 | Ajuste de ordem: a base das fotos (upload validado, armazenamento protegido, capa e galeria sem vínculo) passa da etapa 8 para a etapa 3; o vínculo de fotos com manutenção entra na etapa 4 e com diagnóstico na etapa 5; a etapa 8 fica com projetos e fotos de antes/depois | O cadastro de veículo (p.4 do PDF) já tem "Adicionar foto de capa", e todos os botões precisam executar ações reais. As telas de manutenção e diagnóstico usam fotos antes da etapa 8 | Manter todas as fotos na etapa 8 e deixar a capa sem funcionar até lá |
| 29/09/2026 | Backend em arquitetura em camadas, obrigatória (pedido da Paula): `routes/` → `controllers/` → `services/` → `repositories/` → `banco/` → PostgreSQL, com `entities/`, `config.py` e `main.py`. Cada camada só conversa com a de baixo; `tests/test_arquitetura.py` falha se um `import` furar a regra | Cada parte tem uma responsabilidade clara (endereço, requisição, regra, SQL), o que facilita entender, testar e continuar o projeto. As regras de negócio ficam testáveis sem banco e sem HTTP | Tudo nas funções das routes (mais curto, porém mistura HTTP, regra e SQL) |
| 29/09/2026 | Pasta extra `app/schemas/` para os formatos JSON de entrada e saída (Pydantic) | Separa a entity (o que o sistema guarda) do que a API recebe e devolve; impede, por exemplo, que `senha_hash` apareça numa resposta | Schemas dentro de `controllers/` |
| 29/09/2026 | Entities que representam tabelas serão classes SQLAlchemy 2 (`DeclarativeBase` em `entities/base.py`) mapeando as tabelas **existentes**. Nunca se usa `create_all()`: quem cria e altera o banco são as migrations. `tests/test_entities.py` confere cada entity com as colunas reais. Objetos calculados (como a situação do sistema) são dataclasses | Uma única fonte da verdade para a estrutura (as migrations) e verificação automática de que o código não diverge do banco | Classes Python simples com conversão manual no repository |
| 29/09/2026 | O service controla as transações por `UnidadeDeTrabalho.transacao()` (`banco/sessao.py`); cada requisição tem uma sessão própria, e o que não for confirmado é desfeito ao fechar | Regras como "criar manutenção e resolver diagnóstico" precisam gravar tudo ou nada (etapa 5); quem conhece a regra é o service | Commit automático por requisição (grava parcialmente em caso de falha no meio) |
| 29/09/2026 | Erros de negócio (`services/erros.py`: DadosInvalidos 422, NaoAutenticado 401, AcessoNegado 403, NaoEncontrado 404, Conflito 409) são traduzidos para HTTP num único lugar (`controllers/erros_http.py`), com resposta `{"mensagem": "..."}` | O service não precisa conhecer HTTP, e todas as telas recebem erros no mesmo formato, em português | `HTTPException` espalhada pelos services |
| 29/09/2026 | `gerenciar.py` (criar bancos, migrar, adotar, backup) chama `app/banco/` direto, fora do fluxo Route → Controller → Service → Repository | É ferramenta de manutenção do banco no terminal, não funcionalidade do aplicativo; não há regra de negócio no caminho | Passar pelos services (camadas sem função) |
| 29/09/2026 | Migrations com Alembic, escritas em SQL. A 0001 lê `database/original/meu_veiculo_banco.sql`, confere o SHA-256 (com quebras de linha normalizadas para LF) e executa o conteúdo sem as linhas `BEGIN;`/`COMMIT;`. Cada migration roda na própria transação (`transaction_per_migration`) | O SQL original continua intocado e comprovadamente igual; sem o `COMMIT` interno, uma falha não deixa o banco pela metade. O SQL usa domains, triggers e views, que o autogenerate do Alembic não trata bem | Copiar o SQL para dentro da migration (duas cópias); script próprio de migrations |
| 29/09/2026 | Banco vazio: `gerenciar.py migrar`. Banco criado antes com o SQL original: `gerenciar.py adotar-banco-existente`, que compara a estrutura (colunas, restrições, índices, views, triggers, funções, domains) com o SQL original recriado num esquema temporário desfeito em seguida, e só registra a 0001 se for idêntica. A 0001 se recusa a rodar sobre um banco que já tem a tabela `usuario` | Atende "separar instalação em banco vazio de atualização de banco existente" e "não rodar o script inicial de novo"; diferenças são listadas, nunca corrigidas automaticamente | Marcar a 0001 como aplicada sem conferir |
| 29/09/2026 | Backup com `pg_dump` (formato custom) em `backend/backups/`, automático antes de migrar um banco que já tem migrations aplicadas; recuperação com `pg_restore` (README). A 0001 não tem downgrade automático | Desfazer a 0001 apagaria todos os dados; a recuperação segura é restaurar um backup | Downgrade que apaga as tabelas |
| 29/09/2026 | Usuário próprio do PostgreSQL para a aplicação (`meu_veiculo_app`, sem superusuário, dono dos bancos `meu_veiculo` e `meu_veiculo_teste`). A senha do `postgres` é pedida na hora pelo `criar-bancos` e não fica em arquivo | Menor privilégio: se a senha da aplicação vazar, ela não dá controle do servidor inteiro | Usar o `postgres` na aplicação |
| 29/09/2026 | Fuso `America/Sao_Paulo` fixado em toda conexão do backend (`options=-c timezone=...`) e como padrão dos bancos (`ALTER DATABASE ... SET timezone`). No frontend, datas `AAAA-MM-DD` são formatadas por texto, sem `new Date()` | `CURRENT_DATE` e os `DEFAULT CURRENT_DATE` do SQL dependem do fuso da conexão; `new Date("2026-09-01")` mostraria 31/08 no Brasil | Confiar no fuso configurado no servidor |
| 29/09/2026 | Testes do backend no PostgreSQL real, no banco `meu_veiculo_teste`, que é apagado e recriado; trava: o nome precisa terminar em `_teste` e ser diferente do banco de desenvolvimento. Cliente de teste HTTP com `httpx2` (o `httpx` foi descontinuado para o TestClient) | SQLite não comprova domains, views e triggers; a trava evita apagar o banco de desenvolvimento por engano | SQLite; banco de teste sem trava |
| 29/09/2026 | Frontend chama sempre `/api/...` no próprio endereço; em desenvolvimento, o Vite repassa ao backend (proxy). Não há CORS aberto | Um único endereço para o navegador (e depois o celular), cookies de sessão mais simples e seguros na etapa 2 | CORS liberado com frontend e API em portas diferentes |
| 29/09/2026 | Frontend organizado como projeto React: `pages/`, `components/`, `services/` (único `fetch` em `apiCliente.ts`), `types/`, `utils/`, `styles/`, `tests/`. Fontes Barlow empacotadas com `@fontsource` | Organização conhecida em React, sem forçar os nomes das camadas do backend; fontes sem depender de serviço externo | Espelhar as camadas do backend no frontend; Google Fonts |
| 29/09/2026 | Manifesto e service worker da PWA ficam para depois do login (etapa 2 ou 10), junto com a política de cache | O cache precisa ser pensado junto com o logout, para não deixar dados de um usuário acessíveis | Configurar a PWA já na etapa 1 |
| 29/09/2026 | Versões travadas: Python 3.13, FastAPI 0.141.1, SQLAlchemy 2.1.1, Alembic 1.20.0, psycopg 3.3.6, pytest 9.1.1; React 19.3.0, Vite 8.3.1, TypeScript 7.0.2, Vitest 5.0.2 (`requirements*.txt` e `package-lock.json`) | Instalação reproduzível no computador da Paula | Versões flutuantes |
